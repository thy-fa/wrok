1项目概述

1.1 项目背景

大数据技术专业大三学生进入求职季时，会同时面对三个具体问题：去哪个城市发展、 优先学哪些技能、期望薪资定在多少。

网络上关于"大数据前景好、薪资高"的判断大多是笼统的印象，缺少可验证的数据支撑。 本项目采集前程无忧平台的大数据岗位真实招聘数据， 用数据分析的方法把这三个问题转化为可量化的结论， 让求职决策建立在数据之上，而不是感觉之上。

1.2 项目目标

目标说明
市场画像岗位集中在哪些城市、哪些行业、什么类型的公司，机会量如何分布
门槛结构学历与经验要求的分布，大专生真正够得着的岗位池有多大
薪资量化薪资的整体分布与分位数，以及学历、经验、城市、公司类型对薪资的影响

2数据源与采集方案

2.1 数据源的选择过程

项目最初计划自建爬虫采集招聘平台。在动手前先做了两项前置检查，结论改变了技术路线：

  • robots 协议检查：读取和鲸社区 robots.txt，内容为 Allow: / 但 Disallow: /api/。而数据集的文件列表与下载接口全部位于 /api/ 下——这意味着任何自动下载脚本都必然违反站点的 robots 约定。
  • 页面渲染方式验证：用 Python 直接抓取数据集页面，返回的标题为"工作台"、 文件链接数为 0，证实页面为 JavaScript 动态渲染，直链不在 HTML 中，只能调用接口获取。
决策：放弃自动下载，改为注册登录后手动下载 + 脚本标准化处理的合规路径。 这一判断本身就是项目的一部分——识别合规边界、主动放弃技术手段，比"能爬下来"更能体现工程素养。 面试时被问到"数据怎么来的"，这条理由是可公开陈述的。

2.4 自建采集方案（备选路径）

尽管最终采用公开数据集，采集方案仍完整设计并实现，用于应对数据集不可用或需要增量更新的场景。 核心要点：

环节做法
目标判断F12 → Network → Fetch/XHR 判断是静态 HTML 还是接口 JSON；能走接口就不解析 HTML
采集实现requests + BeautifulSoup；封装 safe_text() 处理 select_one() 返回 None 的情况
频率控制每页间隔 3–6 秒随机休眠，单线程，不并发、不使用代理池
中断策略遇到 403 / 429 立即停止而非重试——被识别后硬重试只会加重风险
断点续采进度写入 progress.txt，支持中断后继续
降级设计未安装 bs4 时自动切换到标准库 html.parser 解析器，保证脚本可运行

2.5 合规边界

  • 频率：单线程、3–6 秒间隔，不对目标站点造成负载压力。
  • robots：采集前校验 robots.txt；读取失败时默认不采集。
  • 法律：不破解验证码与反爬措施（刑法第 285 条）；不采集个人身份信息 （个人信息保护法）；数据仅用于个人学习研究，不作商业用途（反不正当竞争法、著作权法）。
  • 产出：对外只展示聚合统计结果，不对外分发原始数据集。

3数据预处理与清洗

3.1 原始数据存在的真实问题

清洗规则不是凭经验拍脑袋定的，而是先把原始版 4100 条数据完整统计一遍， 针对实际存在的问题逐条设计规则。以下是实测结果：

问题数量后果
重复岗位1281 条（31%）不去重会让所有统计虚高，城市排名失真
整行坏数据475 条城市、经验、描述三者同时为空，属采集失败残留，纯噪音
转义符 \/薪酬 593、公司标签 1497 12-20万\/年 不处理会导致薪资解析失败或被放大 12 倍
列错位学历 46 条、经验 2 条学历列混入"11-16发布"这类日期串，污染分类统计
薪酬缺失82 条无"面议"标记，直接为空，需单独策略处理

3.2 清洗七步

步骤动作理由
0初检：删除无名索引列导出时残留的行号列无业务含义
1清洗转义符 \/ → / 最隐蔽的一步，直接影响后续所有解析
2剔除坏行（关键字段同时为空）信息量不足以支撑任何分析
3去重（职位+公司+城市+薪酬） 用四个键而非三个：三键会误删同公司同城同职位但薪资不同的真实多岗位
4缺失值分策处理薪酬缺失删行（无法推断）；学历/经验/规模填"未知"（保留样本）
5字段解析与类型转换薪资→月薪中位数、城市拆分、学历/经验→有序分类、时间→datetime
6异常值处理合理区间外剔除 + 1%~99% 分位截尾
7删除冗余列并输出产出 jobs_clean.csv，原始层与清洗层分离保存

3.3 薪资口径统一（本项目最关键的一步）

清洗版数据集中薪资存在两套写法且互斥：

字段条数单位
月薪最小值 / 月薪最大值2860元/月
最低年薪 / 最高年薪497元/年

2860 + 497 = 3357，正好互补。若不折算直接分析，等于把年薪当成月薪，结果会离谱到一眼可辨。 统一规则如下：

月薪中位数 = (月薪最小值 + 月薪最大值) / 2            # 月薪口径
月薪中位数 = (最低年薪 + 最高年薪) / 2 / 12           # 年薪口径（÷12 折算）

# 缺失策略：两套口径都没有值 -> 该条不参与薪资分析（不猜、不填 0）

处理后的效果（实测）：

原始写法月薪下限月薪上限月薪中位数
8千-1.6万80001600012000
12-20万/年100001666713333
6-8千600080007000
面议 / 空值——不参与计算
一个踩过的坑：初版解析把 15-25K 算成了 15 而不是 15000—— 因为单位只写在后一个数上。修正逻辑为"任一边有单位则整数区间共用单位，两边都有则各用各的"。 这类问题只有把真实数据跑一遍才会暴露。

3.4 字段类型转换

  • 学历、经验 → 有序分类（Categorical）：不是普通字符串。 经验若按字符串排序，"10年以上"会排在"1年"前面，图表横轴顺序直接错乱。 本项目显式定义顺序：在校生/应届生 → 无需经验 → 1年经验 → 2年经验 → 3-4年经验 → 5-7年经验 → 8-9年经验 → 10年以上经验。
  • 薪资 → 数值型：区间文本解析为数值，才能参与统计与比较。
  • 发布时间 → datetime：原始值为 Excel 日期序列值（如 44881.17），需转换。
  • 公司标签 → 文本清洗：还原转义符后拆分，避免同一标签被计为多个类别。

3.5 异常值处理：为什么用截尾而不是删除

月薪低于 2000 元或高于 100000 元的记录先按规则剔除（多为录入错误或非全职岗位）， 其余极值采用 1%~99% 分位截尾而非直接删除。

原因是：像"3-6 万/月"这类高薪岗位是真实存在的市场信号，直接删除会损失信息， 也会低估高端岗位的存在。截尾只压缩极值对均值的影响，保留样本本身。

5业务结论与项目价值

5.1 结论一：经验的边际收益远大于学历，先入行比先升本科划算

对比数值变化增幅
无需经验 → 1 年经验7.5K → 17.5K+133%
大专 → 本科14.5K → 18.8K+29%
本科+无经验 vs 大专+1 年经验7.5K < 11.5K学历不能替代经验定价

落地动作：接受 7.5K–11.5K 的起薪，先把"1 年工作经验"这个标签拿到手； 参照大专+3-4 年的 17.5K，把 18–24 个月后的目标定在 17.5K 左右。 不要为了够本科门槛而延后入行——这一年工作经验在定价上比一纸文凭更值钱。

口径提醒：这是分组中位数对比，不是因果推断。 薪资差异同时受城市、行业、企业类型影响，本结论用于确定方向， 不足以支撑"只要熬满一年薪资必然翻倍"的推论。

5.2 结论二：岗位数量 ≠ 薪资水平，选"高薪且有量"的城市

错配最典型的两处：南京 348 条但中位仅 14.0K；深圳 257 条却达 20.0K。 而大专岗位数量 TOP 恰恰是 南京（138 条）、深圳（101 条）、合肥（68 条）—— 南京大专岗位最多，但整体薪资水平偏低。

落地动作：城市优先级定为 深圳 > 上海 > 成都（岗位量与薪资兼顾）， 南京作为"先上岸"的备选池；成都（230 条 / 15.0K）属于竞争与回报较均衡的选项。

5.3 结论三：技能决定"能不能进门"，不决定"能拿多少"

需求侧：SQL 40.5%、Java 40.0%、 MySQL 27.2%、Python 22.5%、 Hadoop 20.0%、Spark 18.3%。

但薪资侧几乎拉不开差距（17.5K–18.8K，极差约 1.25K）。技能是准入门槛，不是溢价来源。

落地动作：简历技能栏分两层写——

  • 基础层（必写，覆盖 60%+ 的 JD 关键词）：SQL、Java、Hadoop、Spark、Hive
  • 差异层（选写，用于定向实时数仓岗位）：Flink（8.3%）、 ClickHouse（1.6%）、数据仓库（11.0%）

面试时应把"我会什么"转向"我用它做过什么"——因为技能词大家都会写，项目经历才能区分。

5.4 结论四：期望薪资锚定 P25，投递按企业类型分层

分布：P25 13.3K ｜ 中位数 18.0K ｜ P75 24.0K ｜ P90 31.2K。 全场中位数 18.0K 主要由 3-4 年经验的岗位支撑，不是应届生的锚点。

落地动作：合理报价区间为 7.5K–13.3K，冲刺 14.5K； 若直接报 18.0K 容易被判定为预期脱离市场。 企业类型梯度（合资 27.5K > 外资（欧美） 25.0K > 外资（非欧美） 25.0K > 事业单位 20.5K > 国企 18.8K > 已上市 18.0K > 民营 15.0K）—— 投递可分两池：冲刺池（外资／合资／国企，量少但溢价明显）、 保底池（民营，量大，用于拿 offer 与积累面试经验）。

6总结、局限性与后续优化

6.1 项目总结

本项目以 3357 条真实招聘数据为基础，完成了从数据获取到决策建议的完整闭环：

  • 数据侧：识别并解决了重复、坏行、转义符、列错位、多口径薪资等真实脏数据问题， 薪资可用率提升至 100%。
  • 分析侧：围绕城市、学历、经验、技能、企业类型五个维度展开， 产出 4 张图表与 4 条可执行的求职结论。
  • 结论侧：以数据量化了"经验溢价 > 学历溢价"这一核心判断， 并据此给出了具体的起薪接受区间、城市优先级与技能投入分层。

最大的收获不是画图本身，而是三个习惯：先查数据质量再定规则、 先统一口径再做统计、每个结论都标注适用边界。

6.2 局限性

局限说明
样本偏差数据来自单一平台（前程无忧）单一时点，不能完全代表整个招聘市场； 且以"大数据"为关键词检索，可能遗漏相关岗位
时效性数据为 2022 年 11 月横截面数据，技术栈热度与薪资水平会随时间变化， 结论需结合当下行情使用
薪资口径招聘信息展示的多为薪资区间上限的理论值， 与实际到手薪资、年终奖结构存在差异；本分析取区间中位数，是折中而非精确值
文本提取误差技能词频采用关键词匹配，可能受否定语境影响 （如"不要求 Hadoop"），且无法识别同一技术的不同写法
视角单一仅分析需求侧（企业发布什么岗位）， 未涉及供给侧（求职人数、竞争比），无法判断真实录取难度
因果受限所有结论均为相关性描述。 薪资差异受城市、行业、企业、个人能力共同影响，不能简单归因于单一因素
合规约束受 robots 与平台协议限制，采用手动下载方式获取数据， 无法自动增量更新，数据规模受限于公开数据集

方向具体做法

工程化改造将清洗与分析流程封装为定时任务 + 自动报告， 并接入 ECharts 做交互式仪表盘，提升项目的完整度与展示效果
